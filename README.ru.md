# pg-pagination-bench — руководство на русском

Инструмент измеряет, как ведут себя `LIMIT … OFFSET` и keyset-пагинация (по курсору) **в зависимости от глубины страницы** на вашей PostgreSQL: с прогревом, перемешанными раундами, серверным и клиентским временем, буферами, типом плана и сырым CSV.

> Версия 0.1.0 · Лицензия: [MIT](LICENSE) · Исследование: [R-01](https://interlab.app/blog/paginaciya-offset-keyset-postgresql)

## Зачем

Фразу «keyset быстрее OFFSET» обычно повторяют без цифр для *вашей* таблицы, индекса и глубины. Инструмент превращает её в замер, который можно повторить:

- одна и та же страница из 20 строк — через `OFFSET (N−1)×size` и через `WHERE (created_at, id) < ($1, $2)`;
- проверка, что оба варианта вернули **одинаковые строки** (`rows_match`), иначе сравнение бессмысленно;
- серверное время из `EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)`, клиентское время, буферы, выбранный узел сканирования;
- прогрев не входит в сводку, порядок глубин перемешивается с фиксированным seed, порядок вариантов чередуется;
- всё пишется в CSV, сводка (медиана, p25/p75, min/max) пересчитывается из него.

Это обобщённый стенд исследования InterLAB **«OFFSET или keyset в PostgreSQL 17: замер по глубине страницы»** (12.10.2026, 1 000 000 строк, 3 прогона × 10 раундов): <https://interlab.app/blog/paginaciya-offset-keyset-postgresql>. Тесты пересчитывают опубликованные сырые данные исследования и сверяют медианы с опубликованными.

## Чего инструмент не делает

- Не нагрузочное тестирование: одно соединение, запросы последовательно, без конкуренции.
- Не замер холодного кэша: после прогрева данные обычно в `shared_buffers`.
- Не прогноз для production: одна машина и один набор данных показывают *форму* зависимости, а не ваш бюджет задержки.
- `setup` удаляет и пересоздаёт таблицу — только на одноразовой базе.

## Требования

Node.js ≥ 20 (проверено на 20.20.2 и 24.18.0); PostgreSQL 15.19, 16.14 и 17.11 — на всех трёх `setup` даёт одинаковую контрольную сумму данных.

## Быстрый старт

```bash
npm install
docker run --rm -d --name pgpb -e POSTGRES_PASSWORD=bench -e POSTGRES_DB=bench \
  -p 55417:5432 postgres:17-alpine -c jit=off
export DATABASE_URL=postgres://postgres:bench@localhost:55417/bench

node bin/pg-pagination-bench.mjs setup                  # 1 000 000 строк + индекс (created_at, id)
node bin/pg-pagination-bench.mjs run --out raw.csv      # прогрев + 10 раундов
node bin/pg-pagination-bench.mjs summarize raw.csv      # медианы и разброс
docker stop pgpb
```

Контрольная сумма после `setup` с настройками по умолчанию — `48c42fd798489f22b2847d4427ff3f80`: это те же данные, что в исследовании R-01, число буферов можно сравнивать один к одному.

**Своя таблица:** `--table public.events --order occurred_at,id --depths 1,100,1000`. Колонки сортировки должны вместе быть уникальны (последней — первичный ключ) и желательно покрыты составным индексом в том же порядке. `run` и `explain` выполняют только `SELECT` / `EXPLAIN ANALYZE SELECT`, но глубокий `OFFSET` читает много строк — используйте реплику или копию.

## Проверка

```bash
npm test                         # юнит-тесты + сверка с опубликованным raw.csv R-01 (без базы)
PGBENCH_TEST_URL=postgres://postgres:bench@localhost:55418/bench npm run test:integration
```

## Как честно читать результат

- Смотрите медиану вместе с разбросом: в R-01 медиана самой глубокой страницы OFFSET в трёх свежих контейнерах — 222, 273 и 245 мс.
- Планировщик может выбрать разные планы для одного запроса (в R-01 — `Index Scan Backward` и `Bitmap Heap Scan`); колонка `scan_node` это фиксирует.
- Keyset меняет контракт продукта: нет перехода «на страницу 7 из 50 000», вместо номеров — курсоры.
